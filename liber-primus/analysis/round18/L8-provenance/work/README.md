# `work/` — instrument-control artifacts. NOT corpus material.

Everything in this directory is **generated by the lane's own controls** and must never be
treated as a retrieved Cicada artifact or picked up by a corpus glob.

| file | what it is |
|---|---|
| `control_C2_tampered.asc` | **A DELIBERATELY CORRUPTED COPY** of a genuine 3301 message: one character of the signed body was flipped so that it would produce `BADSIG`. It is the negative control for the verification instrument. It is *not* a Cicada message and its `BADSIG` is *not* a finding. |
| `control_C3_foreign.asc` | A message clear-signed by a throwaway RSA-2048 key generated on this machine, used to prove the verifier does not emit `GOODSIG` for a key it does not hold. Nothing to do with Cicada. |
| `gnupghome-l8/` | The isolated verification keyring, rebuilt from scratch on every run. Holds exactly one primary key: `6D854CD7933322A601C3286D181F01E57A35090F`. |
| `gnupghome-foreign/` | Empty placeholder; the C3 keyring is created under the Linux `/tmp` because gpg-agent cannot open its socket on a drvfs mount. |

`verify_all_signatures.py` explicitly excludes this directory from its scan (`corpus_asc_files()`),
so re-running the lane will not ingest its own controls. Any other tool that walks the tree for
`*.asc` should do the same.

The point of §1.4 of `RESULTS.md` applies here in miniature: a two-byte whitespace difference is
enough to turn an authentic message into a `BADSIG`, so a corrupted control left lying around
unlabelled is exactly how a false "a canon message fails to verify" claim gets born. Hence this file.
